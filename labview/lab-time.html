時間實驗室：Tick Count、逾時判定、時間戳

Tick Count (ms) 傳回一個 U32 毫秒計數。它的起點沒有意義，只能拿兩個值相減算經過多久。U32 最大是 4,294,967,295，再加 1 就回到 0，所以大約每 49.7 天繞回一次。情境：龍門 X 軸開始移動時記下 Tick Count，之後每圈算「現在 − 開始」，超過 8000 ms 就判定動作超時。把起點拉到繞回點附近，按 ▶ 讓時間往前走。

U32 減 U32 的結果也是 U32，跨過繞回點時「借位」剛好把差值補回來：例如開始是 4,294,964,296、現在是 7,000，U32 相減得到 10,000，正好是真正經過的毫秒數。先轉成 DBL 或 I64 這類比較大的型別再減，就變成 7,000 − 4,294,964,296，得到一個很大的負數，「經過時間 > 8000」永遠不成立，超時警報也就永遠不會響。所以兩個 Tick Count 直接用 U32 相減，減完再轉型。這個寫法只要經過的時間不超過 49.7 天都對。

看門狗：有一個心跳值每秒加 1，3 秒沒變就判斷通訊斷線（PLC 判斷 D240 用的也是同一套邏輯）。左邊照建議寫：迴圈每 100 ms 一圈，心跳有變就用 Shift Register 記下當時的 Tick Count，每圈比較「現在 − 上次變化」是否超過 3000 ms。右邊是常見的錯誤寫法：讀一次、Wait 3000 ms、再讀一次比較。兩邊同時跑，讓心跳停住，也按按看 STOP。

用 Wait 等滿 3 秒的寫法有兩個問題：第一，這 3 秒內迴圈什麼都不能做，STOP、畫面更新、其他判斷都得等，操作員會覺得「當掉了」；第二，判斷的時間點被切成 3 秒一格，心跳停住後要等到下一個完整的 3 秒區間結束才會發現，通常比左邊慢。用 Tick Count 比較的寫法，迴圈照常每 100 ms 轉一圈，只是每圈多做一次減法和比較，反應快，判斷也準。同樣的寫法可以用在「動作超過幾秒沒完成就報警」、「每隔幾秒做一次某件事」。

Get Date/Time In Seconds 給的是時間戳（timestamp）：從 1904-01-01 00:00 UTC 起算的秒數，帶小數。Format Date/Time String 依格式碼把它變成文字，紀錄檔的時間欄、每天一個檔的檔名都用它。下面用瀏覽器的時鐘模擬，改格式碼即時看結果。

Tick Count 量間隔，時間戳記「幾點幾分」，兩者別混用。時間戳跟著電腦的時鐘走，電腦自動校時、有人手動改時間，都可能讓它往前或往後跳；拿兩個時間戳相減量動作耗時，碰到校時就可能出現負數。Tick Count 不看時鐘，只是一直往上數，適合量間隔，但它本身不代表任何時刻，不能寫進紀錄檔當時間。
